## 検証コマンド(再現用)

```bash
MK=$(minikube ip)   # 192.168.49.2
# 事前実測
PGPASSWORD=scalaradmin psql -h "$MK" -p 30432 -U scalaradmin -d scalardb_analytics -t -c \
  "SELECT name, provider_type, provider_payload_json FROM scalardb_analytics.registry_data_sources;"
PGPASSWORD=scalaradmin psql -h "$MK" -p 30432 -U scalaradmin -d erpdb -c "\d erp.project_order"
# API(アプリ :8082 起動後)
curl -s "http://localhost:8082/api/catalog/table-keys?dataSource=ds_postgres&namespace=erp&table=project_order"
curl -s "http://localhost:8082/api/catalog/table-keys?dataSource=ds_scalardb&namespace=project&table=project"
curl -s "http://localhost:8082/api/catalog/table-keys?namespace=erp&table=project_order"  # 後方互換
```

## 追試: 新規テーブルを実際に追加して通し確認(2026-07-22、ユーザー要望)

「新テーブル追加 → Analytics カタログ再取込 → View Editor で確認」の実手順を、
**既存 JSON に無い複合 PK テーブル**で実演(単一 PK ばかりの既存と差別化し、複数列・ordinal 順も検証)。

手順と結果:
1. raw PG(erpdb)に `erp.supplier`(PK = `(supplier_code, region_id)` 複合)を作成 + 3 行投入。
2. Analytics CLI(analytics-server-cli pod)で `ds_postgres` を再登録
   (`data-source delete --cascade` → `register`。provider-file は erpdb 全体なので新テーブルを自動収集)。
   ※ CLI pod が Error 残存の場合は `kubectl delete pod` → `apply` で再作成してから。
3. アプリのカタログ再読込 `GET /api/catalog?reload=true` → ツリーに `erp.supplier`(erp 4→5 テーブル)
   と 4 列が出現。
4. `GET /table-keys?dataSource=ds_postgres&namespace=erp&table=supplier`
   → `known=true, partitionKeys=[supplier_code, region_id]`(**複合 PK を ordinal 順**で自動解決)。
5. View Editor で drop → `supplier_code` / `region_id` の**両方が 🔑 ロック**(除外不可)、
   `supplier_name` / `rating` は非キー。証跡 = `docs/results/plan010-20260722/plan010-supplier-composite-key.png`。

→ **キーを一切手入力せず**、接続先スキーマから複合 PK まで自動補完されることを、
新規テーブルの実追加フローで確認。これが新テーブル導入時に実際に通る手順そのもの。

## 結論

plan-010 の非 ScalarDB キー自動補完は、実 DB(minikube 上の raw PostgreSQL)に対し
API・GUI の両面で期待通り動作。SDB 経路の回帰・後方互換フォールバックも維持。MySQL は
resolver 実装済み・ドライバ同梱済みだが、デモに MySQL の非 SDB データソースが無いため
今回は PG のみ実 DB 検証(MySQL は build + supports 判定まで)。
