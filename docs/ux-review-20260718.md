## 追加発見: リフレッシュのデータ消失バグ(E、ユーザー報告 2026-07-18)

報告「データ編集からリフレッシュするとエラー(メッセージ無し)になり View のデータが消えている」を再現・原因特定:

- **E-1 データ消失**: `ViewService.refresh` が truncate → spark クエリの順のため、クエリ失敗時に実体が空のまま残る(vw_order / vw_order2 が実際に消失 → refresh 再実行で復旧済み 2026-07-18)
- **E-2 メッセージ無し**: 失敗原因が `NoClassDefFoundError`(Error 系)で GlobalExceptionHandler(Exception のみ捕捉)を素通りし、ApiResponse 形式でない Spring 素の 500 が返る → GUI がメッセージを取り出せない
- **E-3 根本原因**: `java -jar` 直接起動だと Arrow に必要な `--add-opens=java.base/java.nio=ALL-UNNAMED` が付かない(bootRun には設定済み。E2E が PASS したのは bootRun 起動だったため)

修正方針: E-1=spark クエリ成功後に truncate→insert(create/replace も同順に)、E-2=Throwable ハンドラ追加、E-3=bootJar マニフェストに `Add-Opens: java.base/java.nio` を追加 + README 追記。

### 追加対応2: 更新モジュールの実戦シナリオ(2026-07-18 ユーザー報告起点)

報告「vw_order2 で t2_order_qty を変更したら在庫(t1_stock)に差分反映したい。
読込ノードを足そうとしたが**線の繋ぎ変えが分からなかった**」への対応:

1. **結線 UX**(原因: Drawflow の Delete キー処理はキャンバスにフォーカスがある時のみ有効で、
   線クリック → Delete が実質効かない。右クリック→赤×は動くが発見不能):
   - document レベルの Delete/Backspace ハンドラを追加(入力欄フォーカス時は無効、
     キャンバス内フォーカス時は Drawflow 側に委譲)→ 線選択 → Delete が常に効く(実測 6→5 本)
   - サイドパネルに「線・ノードの操作」ヘルプを常設(接続/削除/繋ぎ替えの手順)
2. **エンジンの書き込み制約の緩和**(ユーザー合意による §2-6 セマンティクス改訂):
   従来はフローの「更新」ノードも「更新可」列しか書けず
   `Column 'stock' is not an updatable column of alias t1` で本シナリオが組めなかった →
   `AfterModel` に writable(= その alias の非キー View 参加列)を導入。
   グリッド直接編集の制約(更新可列のみ)は不変。エディタの Model 変数パネルも
   全参加列を表示(更新可列には「(更新可)」注記)
3. **実例モジュールを vw_order2 に登録**(エディタのページ内 API で組み立て、レイアウト込み保存。
   旧モジュールは scratchpad/backup に退避):
   `start → read(inventory.product, id=$input.id → prod) → var delta = $input.t2_order_qty - before.t2_order_qty
   → var newstock = prod.stock - delta → compare(newstock >= 0) → branch → true: update(t1: stock = newstock) → commit
   / false: abort(在庫不足)`
   ※ 式言語は「1式1演算」のため差分計算は var ノードで段階分割する(M1 制約)
4. **E2E 検証(全 PASS)**: qty 1000→1100 で stock −100(txWrites=2)/
   在庫 1038 の状態で delta 1900 → abort「在庫不足: 受注数の増分が在庫を超えています」・データ不変 /
   復元後 refresh(spark 再クエリ)で backend stock=2147483638 を確認(バックエンド書き戻し実証)。
   同一商品を共有する他行の t1_stock 表示は編集行以外更新されない(refresh で同期)— 仕様どおり

### 追加対応3: INT オーバーフローで在庫が負値になるバグ(2026-07-18 ユーザー報告)

- 事象: vw_order2 の qty 1000→100(減=在庫戻し +900)で t1_stock が **-2147482758** に
- 原因: デモデータの在庫が INT 上限近傍(2147483638)で、フロー式(long 計算)の結果
  2147484538 を `ValueCodec.parse` の INT ケースが `Number.intValue()` で
  **サイレントに 32bit 折り返し**て書き込んだ。比較ノードは long のため通過
- 修正: `toIntChecked` を導入 — INT 列への書き込みは範囲検査し、超過時は
  422「列 'stock' の値が INT の範囲を超えています: <値>」で Tx ごと失敗(データ不変)
- データ修復: 一時モジュール(update t1: stock = 10000 リテラル)差し替え→1編集で
  在庫と qty を同時復旧→差分モジュール復元。**在庫は 2147483638 でなく 10000 に正規化**
  (上限近傍のままだと在庫戻し操作が常に範囲超過エラーになるため。旧値はここに記録)
- 検証: qty 1000→100 → stock 10900 で committed(ユーザーの再現操作が正常動作)/
  オーバーフロー誘発 → 422 エラー・データ不変 / 復元(qty=1000, stock=10000)
